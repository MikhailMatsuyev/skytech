# План реализации

Статусы: `[ ]` не начато, `[~]` в процессе, `[x]` готово.

## Разведка

- [x] Проверить доступность Metacritic обычным HTTP (без headless-браузера) — **сайт на Nuxt 3,
      отдаёт полный JSON прямо в HTML** (`<script id="__NUXT_DATA__">`, формат `devalue`).
      Headless-браузер (Playwright) не нужен — упрощение по сравнению с изначальным планом.
- [x] Разобрать структуру данных: список New Releases (`metacritic.com/game/`), пагинация
      SEE ALL (`/browse/game/all/all/all-time/new/?page=N` → `{items[], total}`), карточка игры
      (`/game/{slug}/` → компоненты `product` (платформы/разработчик/видео/описание),
      `latest-critic-reviews`, `top-user-reviews`, score-summary).

## Этап 1 — скрапер Metacritic (обязательная часть)

- [x] `MetacriticClientService`: HTTP-запрос + извлечение и `devalue`-парсинг `__NUXT_DATA__`
- [x] Парсер списка New Releases (главная `/game/`)
- [x] Парсер пагинации SEE ALL (`/browse/.../new/?page=N`)
- [x] Парсер карточки игры (`/game/{slug}/`): название, обложка, платформы+Metascore,
      Userscore (только для ведущей платформы страницы — см. ограничение ниже), разработчик,
      описание, ссылка на видео (jwplayer embed), тексты отзывов критиков/юзеров
- [x] `ScrapeStateService`: логика "новый день → сброс на New Releases", иначе — следующая
      страница SEE ALL; дедуп через `DailyProcessedGame`
- [x] `GamesService`: upsert игры + `PlatformScore` по slug
- [x] Ручной эндпоинт запуска обхода (`POST /scraper/run`, `GET /scraper/status`)
- [x] Прогнали на реальном сайте 3 батча подряд (New Releases 20 игр → SEE ALL стр.1 24 игры →
      стр.2 24 игры, из них 9 уже виденных — дедуп подтверждён, список SEE ALL "плывёт" между
      заходами, как и предполагалось)

  **Известное ограничение**: Metacritic отдаёт per-platform Userscore только для той платформы,
  которую представляет открытая страница игры (`isLeadPlatform`) — у остальных платформ игры
  Userscore остаётся `null`. Можно закрыть позже доп. запросом на `?platform=` для каждой
  платформы, если останется время.

## Этап 2 — саммари отзывов и похожие игры (обязательная часть)

- [x] `SummaryService`: только локальный Ollama (без облачных LLM и без платных ключей —
      осознанное решение). JSON-ответ `{criticSummary, userSummary}` на основе quote-текстов
      отзывов, вызывается из скрапера на каждую новую игру. Если Ollama недоступна — тихо
      пропускается (не роняет обход)
- [x] Ollama поднят в `docker-compose` (сервис `ollama`, том `ollama_data`), модель
      `qwen2.5:1.5b` — минимальная из тех, что ещё надёжно держит JSON-формат ответа.
      Промпт на английском (не на русском) — модель такого размера ненадёжно следует
      языковой инструкции, а весь остальной контент (описания, отзывы) и так с Metacritic на
      английском, так что это и логичнее
- [x] Похожие игры: `GamesService.findSimilarGames` — эвристика (разработчик + пересечение
      платформ + близость среднего Metascore) → top-N. Проверено на реальных накопленных данных
- [x] Живой прогон на реальных данных: батч из 23 новых игр, 4 из них с отзывами получили
      LLM-саммари (у остальных ещё нет отзывов на Metacritic — слишком свежие), ~4с/игру на CPU

## Этап 4 — веб-интерфейс (обязательная часть)

- [x] `Game.averageMetascore`/`averageUserscore` — денормализованы на upsert (пересчёт из
      `PlatformScore`), чтобы сортировка/фильтр списка были обычным SQL без агрегаций на лету.
      Бэкфилл для уже накопленных 82 игр прогнан
- [x] Побочная находка при бэкфилле: Metacritic отдаёт `userScore.score: 0` (не `null`), когда
      отзывов пользователей ещё 0 — поправили скрапер (проверяем `reviewCount`) и почистили уже
      сохранённые фиктивные нули в БД (75 строк)
- [x] `GET /games` — список (фильтр по платформе `?platform=`, поиск `?search=` по названию,
      сортировка `?sortBy=metascore|userscore|title|updatedAt&order=asc|desc`, пагинация)
- [x] `GET /games/meta/platforms` — список платформ для фильтра в UI
- [x] `GET /games/:slug` — карточка (+ похожие игры через `findSimilarGames`), 404 на несуществующий slug
- [x] Frontend (`apps/web`, React Router): список игр (карточки: обложка/название/платформы/
      Metascore/Userscore-бейджи), карточка игры (платформы+оценки таблицей, описание, LLM-саммари
      критиков/юзеров, ссылка на трейлер, похожие игры с переходом по клику), фильтр по платформе,
      поиск (debounce), сортировка, пагинация
- [x] Backend-эндпоинты проверены вживую (curl): список/поиск/фильтр/пагинация/404 — все ок.
      Фронтенд и API типы компилируются и оба dev-сервера стартуют без ошибок; **визуально в
      браузере не проверено** — расширение Claude in Chrome не подключено в этой сессии, нужна
      ручная проверка на http://localhost:5173

## Этап 5 — деплой MVP обязательной части

- [x] Пользователь берёт свой VPS (Ubuntu 24.04, без панели, SSH-ключ) вместо Railway/Render
- [x] `app.setGlobalPrefix('api')` — API теперь на `/api/*`, чтобы не конфликтовать по путям с
      клиентскими роутами React Router (`/games/:slug` есть и там, и там)
- [x] SPA-фолбэк в `main.ts`: раздача `apps/api/public` (собранный `apps/web`) + явный
      catch-all `/*splat` → `index.html` (важно: Express 5 больше не принимает голый `'*'`)
- [x] Фронтенд ходит по относительному `/api/...` в проде (раньше был хардкод
      `http://localhost:3000` как дефолт — сломало бы прод; для локальной разработки
      `VITE_API_URL` переопределяется в `apps/web/.env`)
- [x] `Dockerfile` (multi-stage: сборка web+api, финальный образ копирует весь `node_modules`
      из build-стадии — проще, чем частичный prod-install для monorepo-воркспейсов) +
      `docker-compose.prod.yml` (postgres + ollama + app на порту 80, том Ollama с моделью
      сохраняется между рестартами)
- [x] Собрано и прогнано полностью локально через `docker-compose.prod.yml`: миграции
      применяются на старте (`prisma migrate deploy`), старые данные (82 игры) сохранились
      через volume, API и SPA корректно работают на одном порту (80)
- [ ] Реальный деплой на VPS пользователя — ещё не сделан, нужен IP сервера
